RAWSETS

01 · Overview

Una app de gym donde el dato importa más que el ego.

RAWSETS registra entrenamientos y, sobre los mismos datos, hace algo que Hevy y el resto no hacen como prioridad: analiza el balance muscular de tu microciclo. Si llevas 18 series de empuje y 4 de tirón, la app te lo dice antes de que la espalda te lo diga.

// Audiencia
Gente que entrena con intención
No principiantes, no atletas pro. Personas que llevan ≥1 año y quieren entender sus datos.
// Diferencial
Balance muscular como feature núcleo
12 grupos finos en storage, 6 agrupados en UI. Detección de desbalances en tiempo real.
// Plataforma
iOS · Android · Web (PWA)
Un solo codebase. Plan B: PWA en iOS hasta justificar pagar Apple Developer Program.
// Fases
3 etapas — móvil → backend → ML
Aprender end-to-end sin saltarse capas. Cada fase desbloquea la siguiente.
02 · Problem

El gym tiene datos. El fitness tiene cheerleaders.

La mayoría de apps de fitness ofrecen lo mismo: registrar reps, contar volumen, recordar tu PR. Sobre eso, montan capas de gamificación: badges, rachas con llamas, mensajes motivacionales. RAWSETS apuesta por lo contrario.

// Tesis

El progreso en el gym no se ve, se mide. Tu cuerpo no necesita aplausos: necesita análisis. Si entrenas en serio durante varios años, lo que falta no son emojis de fuego — falta una herramienta que detecte por ti los puntos ciegos de tu programación.

Lo que sí somos

Directos. Técnicos. Honestos. Concretos. Para quien va al gym sabiendo lo que hace y quiere ver sus datos sin teatro. Una app que mira tu microciclo y te dice "te falta tirón posterior" en vez de "¡increíble entreno, sigue así! 🔥".

Lo que NO somos

Motivacionales. Gamificados. Wellness-coachy. Sociales (sin feed, sin likes). No enseñamos a hacer una sentadilla — quien usa RAWSETS ya entrena. No ofrecemos planes pre-armados — eres tú quien diseña tu rutina.

04 · Technical decisions

Decisiones grandes, explicadas con trade-offs.

Cada elección de stack se evaluó contra alternativas reales, no contra hombres de paja. Estas son las cuatro decisiones más relevantes para el rumbo del proyecto.

Expo + React Native vs Flutter

// Expo elegido

Pros — Expo + RN + TS

  • Reutiliza TypeScript del autor al 100%
  • Tipos compartidos cliente ↔ backend
  • EAS Build resuelve iOS sin Mac
  • OTA updates nativos (EAS Update)
  • Ecosistema y demanda laboral mayor

Por qué no Flutter

  • Dart desde cero — semanas hasta fluidez
  • Rompe los tipos compartidos con backend
  • UI nativa pero rendering propio (menos idiomatic)
  • Ecosistema RN más maduro para integraciones de salud y datos

Monorepo (pnpm workspaces) vs Polyrepo

// Monorepo elegido

Pros — Monorepo plano

  • Cambios atómicos cross-app y cross-package
  • Tipos siempre frescos, sin versionar
  • Un solo pipeline de CI
  • Sweet spot: 1 persona, 1 lenguaje, apps acopladas
  • Estándar de facto en ecosistema TS moderno

Por qué no polyrepo

  • Versionado de tipos compartidos = sobrecarga sin retorno
  • Doble CI sin equipos paralelos
  • Sincronización cross-repo añade fricción
  • Pensado para equipos múltiples con ciclos independientes

PWA-ready desde día 1 (Plan B)

// Aceptado +10% de coste F1

Por qué la disciplina vale la pena

  • Permite Android nativo + PWA iOS sin pagar Apple ($99/año)
  • No pierde audiencia iOS antes de validar producto
  • Aprovecha que Expo compila también a web vía react-native-web
  • Marca el listón en accesibilidad y SEO desde el principio

Las reglas de disciplina

  • Cada dependencia nueva debe soportar web
  • Pantallas únicas responsivas, no bifurcar UI
  • APIs solo-nativo aisladas tras wrappers con fallback web
  • Probar regularmente npx expo start --web

Persistencia local unificada — SQLite + Drizzle

// SQLite en los 3 targets

Cómo se resuelve

  • Móvil: expo-sqlite + driver Drizzle
  • Web: sqlite-wasm + driver Drizzle web
  • Mismo SQL, mismo schema, misma capa de acceso a datos
  • Schema vive en packages/domain, compartido con backend Fase 2

Por qué no IndexedDB o MMKV

  • IndexedDB → no es SQL, requiere reescribir queries por target
  • MMKV/AsyncStorage → KV stores, no relacional
  • Sin un único schema compartido, pierdes la ventaja del monorepo
  • SQLite WASM resuelve el caso con cero divergencia conceptual

07 · Product architecture

Modelo de datos pensado para análisis desde día 1.

El núcleo del modelo es la relación entre ejercicios y grupos musculares con pesos primarios/secundarios. Esto permite que el cálculo de balance no sea un parche posterior, sino una consulta sobre datos que ya tienen la forma correcta.

Exercise id, name, isCustom primaryMuscles: [MuscleGroup] // peso 1.0 en cálculo de balance secondaryMuscles: [MuscleGroup] // peso 0.5 MuscleGroup (enum, 12 valores finos) pecho, dorsal, hombro_anterior, hombro_medio, hombro_posterior, biceps, triceps, antebrazo, cuadriceps, isquios, gluteo, pantorrilla, core Routine id, name, createdAt exercises: [RoutineExercise] // ordenado RoutineExercise exerciseId, position, targetSets, notes? WorkoutSession id, routineId?, startedAt, finishedAt?, notes? WorkoutSet id, sessionId, exerciseId, setNumber, weight, reps, rpe?, completed, restSeconds?

Storage fino, UI agrupada

En base de datos se guardan 12 grupos musculares para tener resolución suficiente para análisis futuros (Fase 3 ML). En la UI por defecto se muestran 6 grupos agrupados (Pectoral, Dorsal, Hombros, Brazos, Piernas, Core) para no saturar visualmente. Tap en una barra agrupada expande al detalle fino.

Cálculo de balance

Para cada grupo muscular en el rango temporal (7/14/30 días), se suma Σ (sets_primarios × 1.0 + sets_secundarios × 0.5). Un grupo es "desbalanceado" si su valor cae por debajo del 50% de la media del usuario en ese mismo período. La lógica vive en packages/domain con tests unitarios.

08 · Roadmap

Tres fases que desbloquean capas distintas.

Cada fase es un objetivo de aprendizaje claro y produce algo demoable. No se salta orden — la Fase 1 alimenta los datos que después la Fase 3 analiza.

// Fase 1 · ACTUAL

MVP móvil local + balance muscular

  • App Expo + RN funcionando en iOS y Android
  • Disciplina Plan B: compila también a web
  • Registro de rutinas, sesiones y sets
  • Dashboard de balance muscular
  • Todo local (SQLite). Sin auth, sin sync
  • Distribución alpha vía Expo Go
// Fase 2

Backend + DevOps + PWA pública

  • Backend Hono + Postgres desplegado
  • Auth + sync entre dispositivos
  • Rutinas compartidas (entrenador → atleta)
  • Modo oscuro activado
  • CI/CD + Docker + observabilidad
  • Landing pública con PWA instalable
  • Google Play (Android nativo)
// Fase 3

Análisis / ML

  • Microservicio Python (FastAPI)
  • Detección de desbalances persistentes
  • Detección de estancamiento
  • Recomendaciones de ajuste de volumen
  • 1RM estimado / periodización sugerida
  • App Store iOS si las métricas justifican
